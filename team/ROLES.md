# 역할별 책임

## 총괄 / PM
- 사용자 요청을 한 문장 목표와 완료 기준으로 바꾼다.
- 과제를 작게 나누고 역할별 결과를 통합한다. 미결정 제품 방향을 숨겨서 확정하지 않는다.
- 검증과 배포까지 담당하고 사용자에게 변경점·확인 결과·남은 제약을 전달한다.
- 완료 기준: 요청을 충족하는 결과가 있고, 실제 배포 여부와 미검증 항목이 명확하다.

## 기획
- 사용 상황은 모바일 출퇴근길, 짧은 시간, 중단과 재방문을 기본으로 한다.
- 기능마다 사용자 문제·첫 행동·성공/실패 흐름·저장 범위·수용 기준을 정의한다.
- 기능 제안과 검증된 수요를 구분한다. 우선순위는 사용자 가치와 구현·운영 부담으로 판단한다.
- 완료 기준: 개발자가 추가 추측 없이 핵심 흐름과 경계 조건을 구현할 수 있다.

## 디자인
- ‘차분한 초록·따뜻한 배경·작은 자유’라는 기존 방향을 유지한다.
- 기본·선택·빈 상태·로딩·오류·저장 성공 상태를 설계한다.
- 작은 화면에서 글줄, 터치 영역, 대비, 폼 라벨, 키보드 포커스와 확대 기능을 확인한다.
- 게임 점수와 금융 정보는 명확하게 구분한다. 체험 게시판을 실제 커뮤니티처럼 꾸미지 않는다.
- 완료 기준: 모바일 화면 흐름과 상태가 명확하고 개발에 필요한 문구·동작 기준이 있다.

## 개발
- 단순한 정적 구조를 유지하며 실제 필요가 생겼을 때 파일과 모듈을 분리한다.
- 안전한 입력 렌더링, 저장 실패, 잘못된 데이터, 외부 수집 실패를 처리한다.
- 실시간 데이터·DB·서버·인증을 흉내 내지 않고 현재 기능을 정확하게 표시한다.
- 완료 기준: 기능 구현, 의미 있는 검증, 원격 반영과 배포 결과 확인.

## 품질 / QA
- 변경한 사용자 흐름을 정상·오류·재방문 조건에서 확인한다.
- 모바일 가로 넘침, 메뉴 상태, 게임 터치, 저장 복원 등 영향을 받는 기존 기능을 점검한다.
- 결함은 재현 단계·기대·실제·영향으로 남긴다. 실제 브라우저 확인과 코드 검증을 구분한다.
- 완료 기준: 중대한 기능 결함 해결, 남은 위험과 검증 불가 항목 명시.

## 콘텐츠 / 운영
- 외부 RSS의 최신성·관련성·중복·언어·출처 표시를 점검한다.
- 원문 제목과 링크 중심으로 제공하며 기사 전체나 이미지를 무단 복제하지 않는다.
- 수집 성공 시각과 게시 시각을 구분하고 자동화 실패 시 지난 데이터를 보존한다.
- 완료 기준: 허위 최신성 표시가 없고, 독자가 출처와 현재 상태를 이해할 수 있다.
