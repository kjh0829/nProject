# 개선 한 건의 작업 흐름

## 1. 요청 → 범위 확정
PM이 한 문장 목표, 이번에 포함할 내용, 완료 기준을 정리한다. 별도 문서는 복잡한 작업에만 필요하다. 정해지지 않은 선호 때문에 독립적인 준비를 멈추지 않는다.

## 2. 기획 → 디자인
기획은 흐름과 저장 범위를 정의한다. 디자인은 필요한 화면과 실패·빈 상태를 정한다. 작은 버그 수정은 한 메모로 충분하다.

## 3. 개발 → 품질 확인
구현 후 변경 범위에 맞는 검증을 한다. UI 변경은 가능한 환경에서 모바일 화면을 확인하고, 기능 변경은 주요 경계값을 확인한다. 파일을 나누는 작업과 동작을 바꾸는 작업은 검토하기 쉽게 범위를 나눈다.

## 4. 릴리스 → 회고
사용자가 요청한 범위의 배포를 진행하고 해당 커밋의 완료 상태를 확인한다. 브라우저 검증의 한계가 있으면 따로 보고한다. 중요한 설계 결정만 DECISIONS.md에 남긴다.

## 상태와 우선순위
- 상태: 제안 → 준비 → 진행 → 검증 → 완료. 실제로 막혔을 때만 차단.
- P0: 데이터 손실·핵심 기능 장애. P1: 사용성·신뢰성. P2: 성장 실험·확장.
- 우선순위는 착수 순서의 제안이며 자동 실행 지시가 아니다.

## 역할 간 전달 예시
기획: “공유 DB 없이도 내가 작성한 글을 다시 찾을 수 있어야 한다.”
디자인: “체험용 안내를 글쓰기 전과 목록에 표시한다.”
개발: “브라우저 저장과 실패 처리를 구현하고 입력값은 텍스트로 렌더링한다.”
QA: “글 작성→새로고침→검색→상세→삭제를 확인한다.”
PM: “실제 사용자 간 공유가 안 되는 제약과 배포 결과를 보고한다.”

## 다중 에이전트로 일할 때
사용자가 명시적으로 요청하면 PM이 역할과 파일 담당을 정한다. 기획·디자인 검토는 병렬 가능하며, 코드 수정은 파일별 소유자를 둔다. QA는 최종 코드를 검증한다. 역할 에이전트의 실행은 해당 작업 동안이며 상시 근무로 표현하지 않는다.
